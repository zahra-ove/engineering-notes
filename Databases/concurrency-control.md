# جزوه: مدیریت هم‌زمانی تراکنش‌ها در دیتابیس (Concurrency Control)

## ۱. مسئله اصلی: Race Condition

فرض کن موجودی یک حساب بانکی ۱۰۰۰ تومان است.

دو تراکنش هم‌زمان اجرا می‌شوند:

* تراکنش A موجودی را می‌خواند: ۱۰۰۰ تومان.

* تراکنش B موجودی را می‌خواند: ۱۰۰۰ تومان.

* تراکنش B مبلغ ۸۰۰ تومان برداشت می‌کند و موجودی را به ۲۰۰ تغییر می‌دهد.

* تراکنش A با استفاده از مقدار قدیمی ۱۰۰۰ تصمیم می‌گیرد ۵۰۰ تومان برداشت کند.

اگر تراکنش A بدون کنترل هم‌زمانی عملیات را انجام دهد، ممکن است موجودی نادرست ثبت شود یا یکی از تغییرات از بین برود.

نکته: استفاده از Transaction به‌تنهایی تضمین نمی‌کند که تمام مشکلات هم‌زمانی حل شوند. رفتار دقیق به Isolation Level و نحوه خواندن و به‌روزرسانی داده بستگی دارد.

سه تکنیک مهم برای مدیریت این مشکلات عبارت‌اند از:

1. Pessimistic Locking

2. Optimistic Locking

3. Atomic Conditional Update

## ۲. Pessimistic Locking (قفل‌گذاری بدبینانه)

در این روش فرض می‌کنیم احتمال تداخل بین تراکنش‌ها وجود دارد؛ بنابراین قبل از تصمیم‌گیری و تغییر داده، قفل می‌گیریم.

در MySQL با موتور InnoDB می‌توانیم از `SELECT ... FOR UPDATE` استفاده کنیم.

مثال:

SQL

```
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1
FOR UPDATE;

-- Check balance in application

UPDATE accounts
SET balance = balance - 500
WHERE id = 1;

COMMIT;
```

### نحوه عملکرد

وقتی تراکنش A دستور `SELECT FOR UPDATE` را اجرا می‌کند، روی ردیف مربوطه قفل می‌گیرد.

اگر تراکنش B بخواهد همان ردیف را به‌روزرسانی کند یا قفل ناسازگاری بگیرد، معمولاً باید منتظر پایان تراکنش A بماند.

قفل با `COMMIT` یا `ROLLBACK` آزاد می‌شود.

البته `SELECT` معمولی در InnoDB عموماً همچنان می‌تواند نسخه مناسب داده را از طریق MVCC بخواند.

### مزایا

* مناسب برای عملیات چندمرحله‌ای که نیازمند کنترل دسترسی هم‌زمان هستند.

* امکان خواندن داده و تصمیم‌گیری روی آن درحالی‌که تغییرات متعارض کنترل می‌شوند.

* جلوگیری از برخی مشکلات Race Condition.

### معایب

* تراکنش‌های دیگر ممکن است منتظر آزاد شدن قفل بمانند.

* احتمال Deadlock وجود دارد.

* تراکنش‌های طولانی می‌توانند عملکرد و توان عملیاتی سیستم را کاهش دهند.

Best Practice: تراکنش‌هایی که قفل می‌گیرند باید کوتاه باشند. تماس با API خارجی یا درگاه پرداخت را داخل تراکنش دارای قفل انجام ندهیم.

## ۳. Optimistic Locking (قفل‌گذاری خوش‌بینانه)

در این روش فرض می‌کنیم تداخل بین عملیات‌ها نسبتاً کم است.

بنابراین از ابتدا قفل طولانی‌مدت نمی‌گیریم؛ هنگام به‌روزرسانی بررسی می‌کنیم که آیا داده از زمان خواندن ما تغییر کرده است یا نه.

یکی از روش‌های رایج، استفاده از ستون `version` است.

ساختار جدول:

SQL

```
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255),
    version INT NOT NULL DEFAULT 1
);
```

ابتدا اطلاعات را می‌خوانیم:

SQL

```
SELECT id, name, version
FROM users
WHERE id = 1;
```

فرض کن مقدار `version` برابر ۳ است.

موقع ذخیره تغییرات:

SQL

```
UPDATE users
SET
    name = 'Ali',
    version = version + 1
WHERE id = 1
AND version = 3;
```

### دو حالت ممکن

حالت اول:

اگر نسخه همچنان ۳ باشد، عملیات انجام می‌شود و نسخه به ۴ تغییر می‌کند.

حالت دوم:

اگر تراکنش دیگری قبلاً اطلاعات را تغییر داده و نسخه را به ۴ رسانده باشد، شرط برقرار نمی‌شود و عملیات انجام نمی‌شود.

برای تشخیص نتیجه باید `RowsAffected` را بررسی کنیم.

اگر صفر باشد، ممکن است رکورد حذف شده باشد یا نسخه آن تغییر کرده باشد. برای تشخیص دقیق، بررسی بیشتری لازم است.

### مزایا

* نیازی به نگهداری قفل از زمان خواندن تا هنگام ذخیره نداریم.

* برای سیستم‌هایی که تداخل نوشتن در آن‌ها کم است مناسب است.

* برای فرم‌های ویرایش اطلاعات کاربرد زیادی دارد.

### معایب

* در صورت بروز تعارض باید راهکار Retry یا Conflict Handling داشته باشیم.

* اگر تعداد تعارض‌ها زیاد باشد، تلاش‌های مجدد می‌توانند هزینه زیادی ایجاد کنند.

* Retry باید با درنظرگرفتن منطق کسب‌وکار انجام شود؛ تکرار کورکورانه عملیات همیشه صحیح نیست.

نکته: Optimistic Locking به معنی نبود قفل در دیتابیس نیست. دیتابیس هنگام اجرای UPDATE همچنان از مکانیسم‌های کنترل هم‌زمانی استفاده می‌کند. تفاوت در این است که اپلیکیشن از زمان خواندن داده، قفل طولانی‌مدت نگه نمی‌دارد.

## ۴. Atomic Conditional Update (به‌روزرسانی اتمیک شرطی)

گاهی نیازی نداریم ابتدا داده را بخوانیم و سپس براساس آن تصمیم بگیریم.

می‌توانیم شرط و عملیات تغییر را داخل یک دستور SQL قرار دهیم.

مثلاً می‌خواهیم ۵۰۰ تومان از حساب برداشت کنیم، به شرطی که موجودی کافی باشد.

SQL

```
UPDATE accounts
SET balance = balance - 500
WHERE id = 1
AND balance >= 500;
```

در این روش دیتابیس شرط و تغییر را به‌عنوان بخشی از یک عملیات UPDATE اجرا می‌کند.

### سناریو

فرض کن موجودی حساب ۱۰۰۰ تومان است.

تراکنش B ابتدا ۸۰۰ تومان برداشت می‌کند و Commit می‌شود.

موجودی جدید ۲۰۰ تومان است.

حالا تراکنش A دستور بالا را اجرا می‌کند.

چون موجودی فعلی کمتر از ۵۰۰ تومان است، شرط برقرار نمی‌شود و هیچ ردیفی تغییر نمی‌کند.

در MySQL/InnoDB، این UPDATE یک عملیات نوشتن است و ارزیابی آن با کنترل قفل‌ها و وضعیت جاری ردیف انجام می‌شود؛ بنابراین صرفاً به مقدار قدیمی‌ای که قبلاً با SELECT معمولی خوانده‌ایم متکی نیست.

### تشخیص موفقیت

در Go:

Go

```
result, err := db.ExecContext(
    ctx,
    `UPDATE accounts
     SET balance = balance - ?
     WHERE id = ?
     AND balance >= ?`,
    amount,
    accountID,
    amount,
)

if err != nil {
    return err
}

affected, err := result.RowsAffected()
if err != nil {
    return err
}

if affected == 0 {
    return errors.New(
        "insufficient balance or account not found",
    )
}
```

در این مثال باید پکیج `errors` را import کنیم.

### مزایا

* پیاده‌سازی نسبتاً ساده.

* مناسب برای تغییرات شرطی روی یک ردیف.

* جلوگیری از تصمیم‌گیری بر اساس مقدار قدیمی برای شرطی که داخل UPDATE نوشته شده است.

* بدون نیاز به اجرای جداگانه SELECT و نگهداری قفل از آن لحظه.

### محدودیت

اگر عملیات شامل چند تغییر وابسته باشد، یک UPDATE به‌تنهایی کافی نیست.

مثلاً انتقال پول بین دو حساب شامل کاهش موجودی حساب مبدأ و افزایش موجودی حساب مقصد است.

در این حالت باید تغییرات وابسته را داخل یک Transaction انجام دهیم و کنترل هم‌زمانی مناسب نیز داشته باشیم.

## ۵. تفاوت Atomicity و Atomic Conditional Update

این دو مفهوم یکسان نیستند.

Atomicity در ACID:

یعنی تمام تغییرات داخل یک Transaction یا با هم Commit شوند یا با هم Rollback شوند.

مثلاً:

SQL

```
BEGIN;

UPDATE accounts
SET balance = balance - 500
WHERE id = 1;

UPDATE accounts
SET balance = balance + 500
WHERE id = 2;

COMMIT;
```

اگر عملیات به‌درستی داخل تراکنش مدیریت شود، تغییرات به‌صورت یک واحد Commit یا Rollback می‌شوند.

اما صرف استفاده از Transaction کافی نیست تا مطمئن شویم موجودی حساب مبدأ منفی نمی‌شود.

Atomic Conditional Update:

یعنی شرط و تغییر را در همان دستور UPDATE قرار می‌دهیم:

SQL

```
UPDATE accounts
SET balance = balance - 500
WHERE id = 1
AND balance >= 500;
```

برای انتقال پول، می‌توانیم این دستور شرطی را داخل Transaction اجرا کنیم، نتیجه آن را بررسی کنیم و فقط در صورت موفقیت، حساب مقصد را افزایش دهیم.

بنابراین Atomicity و Concurrency Control مکمل یکدیگرند.

### نکات مهم برای Production

* Transactionها را تا حد امکان کوتاه نگه داریم.

* بعد از UPDATE شرطی، نتیجه `RowsAffected` را بررسی کنیم.

* در Optimistic Locking برای Conflict Handling سیاست مشخص داشته باشیم.

* در Pessimistic Locking احتمال Deadlock و Lock Timeout را در نظر بگیریم.

* در عملیات مالی، علاوه بر کنترل موجودی و هم‌زمانی، Idempotency را نیز برای جلوگیری از اجرای تکراری یک درخواست در نظر بگیریم.

جمع‌بندی: Transaction تضمین می‌کند مجموعه‌ای از تغییرات به‌صورت اتمیک Commit یا Rollback شوند؛ اما برای جلوگیری از تصمیم‌گیری بر اساس داده قدیمی و بروز Race Condition باید متناسب با مسئله، مکانیزم کنترل هم‌زمانی مناسبی نیز طراحی کنیم.
